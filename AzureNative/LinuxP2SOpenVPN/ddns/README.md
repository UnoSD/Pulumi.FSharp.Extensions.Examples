# Azure DNS updater

Run the updater on one always-on Debian server. It updates a dedicated Azure **public DNS A record** with your public IPv4. The VPN uses that record's FQDN.

The Pulumi project creates the updater's application, service principal, client credential and record-scoped permissions. The Bash exporter generates the two local configuration files. The updater itself needs only Python 3, CA certificates and outbound HTTPS.

## 1. Configure the Pulumi project

Use an existing authoritative Azure public DNS zone and a dedicated A record. The example does not create or manage the record's changing address, so future Pulumi updates cannot revert the updater's changes.

For `ip.example.com`, run these commands from `LinuxP2SOpenVPN` with the intended stack selected:

```sh
pulumi config set VPN:ddnsEnabled true
pulumi config set VPN:ddnsResourceGroup rg-public-dns
pulumi config set VPN:ddnsZoneName example.com
pulumi config set VPN:ddnsRecordName ip

pulumi config set VPN:s2sEnabled true
pulumi config set VPN:s2sGatewayFqdn ip.example.com
pulumi config set --path 'VPN:s2sAddressPrefixes[0]' 192.168.1.0/24
```

Replace the examples with your values. Configuration is used directly, without custom value validation. Use `@` for the DNS zone apex. DNS identity creation is independent of `s2sEnabled`, so you can prepare the updater separately.

| Setting | Purpose |
|---|---|
| `VPN:ddnsEnabled` | Create the updater identity and permissions; defaults to false. |
| `VPN:ddnsResourceGroup` | Existing DNS zone resource group. |
| `VPN:ddnsZoneName` | Existing public zone, such as `example.com`. |
| `VPN:ddnsRecordName` | Relative A-record name, such as `home` or `@`. |
| `VPN:ddnsSubscriptionId` | Optional DNS subscription override; defaults to Azure Native's subscription. |
| `VPN:ddnsCredentialVersion` | Change this value to replace the client credential; defaults to `1`. |

The AzureAD and Azure Native providers must use the **same tenant**. Configure their credentials through your normal Pulumi provider authentication. The identity deploying this stack needs both Entra application/service-principal management permissions and Azure RBAC role-definition/assignment permissions. Those deployment permissions are separate from the updater's restricted runtime role. The pinned AzureAD provider documents `Application.ReadWrite.All` or `Directory.ReadWrite.All` for service-principal-based provisioning; owners alone do not make `Application.ReadWrite.OwnedBy` sufficient for this version. Do not grant those directory permissions to the generated updater identity.

### Resources and permissions

The code uses `Pulumi.FSharp.AzureAD` **5.14.0.3**, compatible with the existing Pulumi dependency set, for:

- A single-tenant application.
- Its service principal, owned by the AzureAD deployment identity.
- An application password, generated by Entra and valid for **8760 hours** from creation.

Azure Native creates a custom role with only:

```text
Microsoft.Network/dnsZones/A/write
```

The role is defined at subscription scope and available in the DNS resource group. Its **actual assignment** is only at:

```text
/subscriptions/SUBSCRIPTION/resourceGroups/GROUP/providers/Microsoft.Network/dnsZones/ZONE/A/RECORD
```

The principal receives no zone-wide or subscription-wide assignment, no read/list/delete operation and no Graph API permissions. Record write permission can still change or empty that record, so protect the credential. State-managed UUIDs keep role identities stable; assignment UUID keepers track principal, role and record scope.

The application-password resource explicitly marks `value` as secret, and the exported credential is also explicitly secret. The small F# builder extension exposes that resource option because the pinned AzureAD builder lacks it.

Review the plan and deploy when ready:

```sh
pulumi preview
pulumi up
```

The existing VPN gateway migration caveat in the parent README still applies. Directory/RBAC propagation can take time; a successful resource deployment is not a live authentication or tunnel test.

## 2. Export the updater configuration

Run on the machine that has Pulumi access to this stack:

```sh
bash ddns/export-config.sh "$HOME/dns-updater-export"
```

Or select a stack explicitly:

```sh
bash ddns/export-config.sh "$HOME/dns-updater-export" organization/project/stack
```

Bash, Python 3 and the Pulumi CLI are needed for this step. The destination must be new and its parent must already exist. The script reads only:

- `DnsUpdaterConfig`: tenant/client/subscription IDs, resource group, zone and record.
- `DnsUpdaterClientSecret`: retrieved with `--show-secrets` into a protected temporary file, never printed.

It creates a private directory with `config.json` and `client-secret`, using modes 0700/0600 on Linux. Existing destinations are not overwritten. The generated config points to the installed secret path `/etc/azure-dns-ddns/client-secret`; edit that one field if you choose another installation path. The exported local files can therefore be copied to the target without leaving a deployment-machine path in the configuration.

`DnsUpdaterCredentialExpiresAt` is also exported for expiry tracking. The Entra client credential is **not** the VPN's `SiteToSiteSharedKey`. Treat the exported directory and Pulumi state as sensitive. Keep it outside Git, use a secure transfer method, and remove temporary copies once installed.

## 3a. Install on Debian

Copy the `ddns` scripts/units and exported files securely to Debian. The example below is for a **fresh installation**, run from the `ddns` directory. If an account, config or unit already exists, inspect and merge deliberately rather than blindly overwriting it.

```sh
sudo apt-get update
sudo apt-get install python3 ca-certificates
sudo useradd --system --user-group --home-dir /var/lib/azure-dns-ddns --shell /usr/sbin/nologin azure-dns-ddns

sudo install -d -m 0755 /usr/local/lib/azure-dns-ddns
sudo install -m 0644 azure_dns_ddns.py /usr/local/lib/azure-dns-ddns/azure_dns_ddns.py
sudo install -d -o root -g azure-dns-ddns -m 0750 /etc/azure-dns-ddns
sudo install -o azure-dns-ddns -g azure-dns-ddns -m 0600 "$HOME/dns-updater-export/config.json" /etc/azure-dns-ddns/config.json
sudo install -o azure-dns-ddns -g azure-dns-ddns -m 0600 "$HOME/dns-updater-export/client-secret" /etc/azure-dns-ddns/client-secret

sudo install -m 0644 azure-dns-ddns.service /etc/systemd/system/azure-dns-ddns.service
sudo install -m 0644 azure-dns-ddns.timer /etc/systemd/system/azure-dns-ddns.timer
sudo systemctl daemon-reload
sudo systemctl start azure-dns-ddns.service
sudo journalctl -u azure-dns-ddns.service --no-pager -n 20
```

Adjust the exported-file source paths if you transferred them elsewhere. The service creates its private state directory. After the manual run succeeds and public DNS is correct:

```sh
sudo systemctl enable --now azure-dns-ddns.timer
systemctl list-timers azure-dns-ddns.timer
```

The timer runs roughly every five minutes. To stop updates:

```sh
sudo systemctl disable --now azure-dns-ddns.timer
```

## Operation and rotation

The updater assumes its configuration and arguments are correct. Each run detects the public IPv4, authenticates, and sends one unconditional PUT. It does not read the DNS record, compare the previous address, send ETags, or verify through a follow-up GET. A successful HTTP 200/201 is the acknowledgment.

Each write replaces the A record set with **one address and TTL 300 seconds**. Existing addresses, TTL and metadata are not preserved. Manual edits are intentionally overwritten on the next run, even when the public IP has not changed. Use this only for a record owned by the updater. The PUT endpoint can create a missing record if its assignment still authorizes that scope; initial setup should pre-create the record for record-scoped RBAC.

HTTPS verification, non-redirecting credential requests, bounded requests, safe error messages, a local lock and persisted Retry-After cooldowns remain. There are no immediate write retries; after a failed or ambiguous PUT, the next scheduled run writes the current address again.

Use a publicly delegated zone, not Private DNS. The lookup defaults to `https://api.ipify.org`; an optional `publicIpUrl` in the installed JSON can select another trusted IPv4 HTTPS endpoint. Ensure requests leave through the home WAN, not an Azure full-tunnel VPN or another proxy. Allow for the timer, DNS caches and Azure's FQDN refresh/reconnection delay. DDNS does not solve CGNAT or replace IPsec/firewall/routing configuration.

The password is not rotated on every deployment. Before its expiry, change the version and deploy:

```sh
pulumi config set VPN:ddnsCredentialVersion 2
pulumi preview
pulumi up
```

Export to a **new** directory, stop the updater timer, deliberately replace the installed credential/config with the exported files and correct ownership/modes, then test and restart the timer. Credential replacement can interrupt updates until the new file is installed. The script intentionally does not overwrite an existing export directory. Disabling `VPN:ddnsEnabled` and applying the change deletes its identity, credential, role/assignment and UUID resources; the existing DNS record is not deleted.
