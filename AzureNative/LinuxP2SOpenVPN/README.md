# LinuxP2SOpenVPN

Creates a **Public IP**, a **Virtual Network** and a **VPN Gatway** gateway in **Azure**;

It creates then a **P2S** configuration with **OpenVPN** generating all the certificates and keys within **Pulumi**.

Once the deployment is completed, it will output a valid **OpenVPN** configuration file, use:

`pulumi stack output OpenVpnFile --show-secrets > AzureVPN.ovpn`

And you can then import the file in a VPN client and connect straightway.

Works also on **GNU/Linux**; tested with the **NetworkManager** UI, importing the output file.

## Optional S2S connection

The same route-based gateway can also connect to a remote network using **IPsec/IKEv2** and a pre-shared key. This adds a **Local Network Gateway** and a **VPN Connection**; the existing OpenVPN P2S configuration, certificates and outputs remain unchanged.

S2S is disabled by default. Configuration is read explicitly from the `VPN` namespace. To enable one remote site using a DDNS hostname, run the following from this directory with your Pulumi stack selected:

```sh
pulumi config set VPN:s2sEnabled true
pulumi config set VPN:s2sGatewayFqdn your-home.example.net
pulumi config set --path 'VPN:s2sAddressPrefixes[0]' 192.168.10.0/24
pulumi config set --path 'VPN:s2sAddressPrefixes[1]' 192.168.20.0/24
```

Replace the example hostname and CIDRs with your publicly resolvable DDNS hostname and the private networks behind your remote VPN device. For example, an OpenWrt LAN interface at `192.168.1.1` with netmask `255.255.255.0` corresponds to `192.168.1.0/24`. These prefixes tell Azure which home networks to route through the tunnel; they are not your public IP or the Azure networks.

S2S uses only `VPN:s2sGatewayFqdn`. Configuration values are passed directly to the providers without custom validation.

The hostname is passed directly to Azure's Local Network Gateway `fqdn` property; Pulumi does not resolve and pin its current IP. Configure OpenWrt or your DDNS updater to maintain a DNS record resolving to a single public IPv4 address. No Pulumi update is needed when that address changes. Azure refreshes its DNS cache every five minutes and resolves disconnected tunnels, so IP changes can interrupt connectivity. DDNS does not remove NAT/firewall restrictions or solve CGNAT by itself.

| Configuration | Description |
|---------------|-------------|
| `VPN:s2sEnabled` | Optional boolean, defaults to `false`. |
| `VPN:s2sGatewayFqdn` | Remote VPN device's public DNS/DDNS hostname; required when enabled. |
| `VPN:s2sAddressPrefixes` | Array of remote private network CIDRs; required when enabled. |

### Shared key

When S2S is enabled, a managed `RandomPassword` resource generates a 64-character alphanumeric key. The Random provider retains it in stack state, so unchanged deployments reuse the same key rather than generating one on every run. The connection input and the `SiteToSiteSharedKey` output are secret, and the key is always generated by Pulumi. Generation occurs through the provider during deployment, not by generating a value in this program on every execution.

After deployment, retrieve the key locally and configure the same value as the IKE pre-shared key on OpenWrt/strongSwan:

```sh
pulumi stack output SiteToSiteSharedKey --show-secrets
```

This explicitly reveals the key in your terminal. Avoid captured terminal logs, do not commit it, and protect your Pulumi state and its secrets-provider credentials. Keep the OpenWrt copy in a restricted secret configuration file.

Replacing the random resource, losing its state, or disabling and re-enabling S2S can change the key and interrupt the tunnel. Coordinate the matching OpenWrt update. The program does not automatically rotate the key or configure OpenWrt.

Remote networks must not overlap the Azure VNet (`10.255.0.0/16`), the P2S client pool (`172.16.201.0/24`), or other connected networks. This example uses static routes with BGP disabled, the Azure default IPsec/IKE policy, and no custom policy-based traffic selectors. The gateway remains **RouteBased**.

After addressing the deployment prerequisites below, review and deploy:

```sh
pulumi preview
pulumi up
pulumi stack output VpnGatewayPublicIp
```

`VpnGatewayPublicIp` and the secret `SiteToSiteSharedKey` output are present only when S2S is enabled. The connection ID is not exported because neither the remote VPN device nor the updater needs it. Configure your remote VPN device with `VpnGatewayPublicIp` as its Azure peer, the matching pre-shared key, compatible IKEv2/IPsec settings, and routes to `10.255.0.0/16`. Allow the required IKE/IPsec traffic through the intervening firewalls, including UDP 500/4500 for IKE/NAT traversal as appropriate for your device.

The code configures only the Azure side. Check that the VPN connection reports **Connected**, then verify bidirectional traffic and return routing between actual workloads. The example creates only `GatewaySubnet`, not a workload subnet or test VM; do not place workloads or an NSG in `GatewaySubnet`.

Adding this non-BGP S2S connection does not by itself provide P2S-client-to-remote-site transit. That requires a separate routing design; see [Azure P2S routing](https://learn.microsoft.com/en-us/azure/vpn-gateway/vpn-gateway-about-point-to-site-routing).

To return to P2S-only, run `pulumi config set VPN:s2sEnabled false` and review `pulumi preview`. The next `pulumi up` will **delete the S2S connection, local network gateway and any managed S2S random-key resource**, while retaining the P2S gateway.

## Keep an Azure DNS hostname updated

The [Azure DNS updater](ddns/README.md) updates a dedicated public A record with your home IPv4. Enable `VPN:ddnsEnabled` and set `VPN:ddnsResourceGroup`, `VPN:ddnsZoneName` and `VPN:ddnsRecordName` to have Pulumi create the AzureAD application, service principal, secret credential and a custom write-only role assigned only to that A record. The existing zone and record remain externally managed.

After deployment, generate the updater files without printing the client secret:

```sh
bash ddns/export-config.sh "$HOME/dns-updater-export"
```

The script reads the selected Pulumi outputs and creates `config.json` plus a separate protected `client-secret` file. The updater uses a small standard-library Python script and assumes its config/arguments are correct. Each run writes one A address with TTL 300, replacing manual changes without reading the old record or using ETags. Credentials stay out of logs.

The linked instructions cover provider/deployment permissions, one-year credential expiry and explicit rotation, a Debian timer, and the OpenWrt alternative. No device installation is performed by `pulumi up`. The DNS updater runs at home; the VPN only consumes its FQDN.

## Existing deployment prerequisites

The example targets .NET 6 and uses `Pulumi.FSharp.AzureNative` **3.0.0.26** (AzureNative 3.0.0), with Pulumi/Pulumi.FSharp 3.77.0 and FSharp.Core 6.0.6. Following the supplied refactor, it now uses a **Standard/Static public IP**, but retains the **VpnGw1** gateway SKU. The non-AZ gateway SKU is still legacy and is not suitable for a new deployment under current Azure requirements. Changing an existing Basic/Dynamic IP to Standard/Static is not a migration procedure: review replacement/downtime implications before applying this code to an existing stack.

- For a new deployment, retain the **Standard/Static public IP** and select a supported **AZ gateway SKU**, such as `VpnGw1AZ` (both SKU name and tier), appropriate for your region.
- For an existing deployment, follow Microsoft's [VPN gateway migration guidance](https://learn.microsoft.com/en-us/azure/vpn-gateway/basic-public-ip-migrate-about) and [gateway SKU consolidation guidance](https://learn.microsoft.com/en-us/azure/vpn-gateway/gateway-sku-consolidation), then reconcile the Pulumi configuration/state before adding S2S. Do not assume editing the public IP or gateway SKU in this example is a safe in-place migration.
- Use a compatible .NET runtime for the existing target; .NET 6 remains out of support.
- The AzureNative major upgrade changes default Azure API versions (including Network 2024-05-01 and ResourceGroups 2024-03-01). Logical resource names are unchanged, but review a real `pulumi preview` for updates/replacements before deployment. Offline mocks cannot determine migration effects.
- A stack that previously supplied `VPN:s2sSharedKey` now generates a managed key instead. Update the remote peer with the new `SiteToSiteSharedKey` output; existing generated-key stacks retain the same random-resource identity.

See also [Azure VPN Gateway FAQ](https://learn.microsoft.com/en-us/azure/vpn-gateway/vpn-gateway-vpn-faq) and the [site-to-site configuration tutorial](https://learn.microsoft.com/en-us/azure/vpn-gateway/tutorial-site-to-site-portal).
